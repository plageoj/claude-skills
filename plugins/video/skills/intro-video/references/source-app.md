# アプリのデモを収録する

ブラウザで動くアプリを Playwright で操作し、台本の時刻どおりのテイクを撮る。人が手で操作するより、タイミングが VO と揃い、何度でも同じテイクを撮り直せる。

デスクトップアプリでも、同じ UI のブラウザ版（開発サーバー、Web デモ）があればそれを撮る。実機でしか見せられないもの（起動の速さ、ウィンドウの開閉）は、ユーザーが自分で撮る手持ち素材にしてもらう。

## 収録スクリプトの設計

1 本の Node スクリプト（例: `video/record-demo.mjs`）にまとめる。Playwright は対象リポジトリにすでに入っていればそれを `createRequire` で読み、なければ作業ディレクトリに入れる。

### 構成

1. **定数**: 開発サーバーの URL、ビューポート（1920×1080）、テイクの開始・終了時刻（動画全体の絶対時刻）、出力先
2. **デモ用データ**: 画面外で作っておくデータと、テイク中に入力する文字列。実在の人名・メールアドレスは使わない
3. **タイムライン**: `[絶対時刻, 操作]` の配列。台本の時刻をそのまま書き、横に VO の一節をコメントで添える
4. **ドライバー**: `press`（キーの組み合わせや連続入力）、`type`（1 文字ごとの遅延つき）、`click`（要素までカーソルを動かしてからクリック）、アプリ固有の操作（項目を作る、など）をまとめた小さな関数群。ダイアログや入力欄の表示・非表示などの状態を `waitFor` で待ってから次へ進む
5. **準備（画面外）**: ログイン、テーマや文字サイズの設定、デモ用データの作成、未リリース機能のボタンを隠す（`display: none` を注入）、最初の画面とフォーカス位置を決める
6. **操作の見える化**: キー操作のアプリなら押したキーを、マウス操作のアプリならカーソルとクリックを、画面に出すオーバーレイをページに注入する
7. **キャプチャ**: CDP の `Page.startScreencast` で PNG を受け取り、時刻つきで保存する
8. **リサンプル**: 可変レートのフレームを、一定の fps（60）の連番に並べ直す
9. **エンコード**: ffmpeg で H.264（`-crf 12 -preset slow -pix_fmt yuv420p`）にする

### 時刻の合わせ方

- テイク開始からの経過時間を `performance.now()` で測り、各操作の絶対時刻まで待ってから実行する。前の操作が遅れて時刻を過ぎていたら、どれだけ遅れたかを警告で出す。黙って遅れると VO とずれたまま気づけない。
- 最後の操作のあと、テイク終了時刻まで待ってから止める。テイクの長さを台本の区間と一致させるため。

### 操作はページに描いて見せる

Playwright の入力は OS を通らないので、OS のキー表示ツール（キーキャスター）にも、マウスカーソルにも映らない。何をしたかが見えないデモは、視聴者には画面が勝手に変わっているように見える。見せたい操作を、`page.addInitScript` で注入した要素で描く。

- **キー操作**: `keydown` を拾って画面の隅に表示する。修飾キーは `Ctrl+Shift+P` のように組み合わせて、大文字は `Shift+L` と出す。
- **マウス操作**: `mousemove` に追従する偽のカーソルを描き、クリックの位置に波紋を出す。`page.mouse.move(x, y, { steps })` で段階を付けて動かし、瞬間移動させない。クリックの前に 0.2〜0.3 秒止めると、どこを押したかが追える。
- 準備中の操作は映さない。テイク開始時にフラグを立ててから表示を始める。

### キャプチャを screencast にする理由

Playwright の `recordVideo` は画質が低く、fps も一定しない。CDP の screencast なら画面のピクセルそのままの PNG が、描画されたときだけ届く。届いたフレームを、一定間隔の時刻ごとに「その時刻以前で最後のフレーム」で埋めれば、一定 fps の連番になる。ハードリンクで並べればディスクも食わない。

### 撮り直しやすくする

- `--live` を付けるとブラウザを表示して実行し、OBS などで撮れるようにする。headless の screencast がうまくいかない環境への逃げ道になる。
- `DEBUG=1` で、各操作のあとに画面の状態（フォーカスや選択中の要素、開いている画面）をログに出す。操作を足したり削ったりしたとき、狙った状態になっているかを確かめるのに使う。
- 出力先を消すときは、中身（生フレーム、連番、mp4）だけを消す。シェルのカレントディレクトリが出力先の中にあると、Windows ではディレクトリごと消せない（EBUSY）。
- 生フレームはリサンプル後に消す。

## 台本から操作を組むときの注意

- 操作に使うキーやボタンは、ソースコードか実際の画面で確かめる。台本に書いた操作とずれていたら、台本の方を直してユーザーに伝える。
- 先に短い探りのスクリプトで、操作ごとの画面の変化を確かめる。たとえば「作成ボタンで名前の入力欄まで開くか」「検索結果が反映されるまで待ちが要るか」。思い込みでタイムラインを組むと、撮ってから気づくことになる。
- 一覧の端での移動、前回の位置の記憶など、操作の結果はアプリごとに違う。どこに行き着くかは `DEBUG=1` の出力で確かめる。
- 要素は表示上の文言やロール（`getByRole`）で指定する。座標で指定すると、文字サイズや画面の幅を変えたときに外れる。
- 通信を伴う操作は、応答の速さで時刻がぶれる。デモ用のデータはローカルかモックで返し、外部サービスに依存しないようにする。
- 文字の入力は 1 文字 35〜80 ms 程度にする。速すぎると読めず、遅すぎると VO に追いつかない。
- キー操作のアプリで、ダイアログをマウスで閉じるとフォーカスが外れ、以降のキー操作が効かなくなることがある。開閉の手段を、テイク中の操作とそろえる。

## 出力

- `out/frames/000000.png …`: 60 fps の連番（テイク開始が 0 枚目）
- `out/demo.mp4`: その H.264
- 1 本撮ったら、数か所のフレームを切り出して見る。操作の結果、キー表示やカーソル、隠したはずのボタンが映っていないかを確かめる。
