# 紹介動画の制作

アプリのデモかスライドを素材に、ナレーション（VO）と字幕の付いた数分の紹介動画を作る。工程は次の 7 つで、どれか一部だけを頼まれたときもその工程の節に従う。

1. 入力をそろえる
2. 台本と字幕を書く
3. 映像素材を作る（アプリは収録、スライドは画像化）
4. VO を用意する
5. Remotion で編集して書き出す
6. 公開前に確認して報告する
7. 台本・字幕が直されたら書き出し直す

この skill は手順書で、コードは同梱しない。収録スクリプトや Remotion プロジェクトは、ここに書いた設計に沿ってその場で書く。詳細は工程ごとの参照ファイルにある。

| 参照ファイル | 読むとき |
|:--|:--|
| `references/source-app.md` | アプリのデモを Playwright で収録するとき |
| `references/source-slides.md` | スライドを素材にするとき |
| `references/audio.md` | VO を作る・受け取るとき、音量をそろえるとき |
| `references/remotion.md` | 編集・書き出しをするとき |

## 1. 入力をそろえる

会話やファイルから読み取れないものは、台本を書き始める前に AskUserQuestion でまとめて訊く。言語や尺が後から変わると、台本・字幕・VO・収録のすべてを作り直すことになるため。

| 情報 | 必須 | 用途 |
|:--|:--|:--|
| 動画の目的と提出先 | 必須 | コンテスト応募・LP・SNS など。提出先の規定（尺の上限、形式、AI 生成物の可否）を確かめる。URL があれば読む |
| 素材 | 必須 | アプリ（起動方法と URL）か、スライド（PDF / Marp / pptx / Google Slides） |
| 音声と字幕の言語 | 必須 | 毎回訊く。例: 英語音声＋日本語字幕（吹き替え映画風）、日本語音声＋英語字幕、字幕なし |
| 視聴者 | 必須 | 前提知識と、字幕を焼き込むか CC で別に出すか |
| VO の作り方 | 必須 | srt-dubbing で合成するか、ユーザーが録音したファイルを渡すか（`references/audio.md`） |
| 触れてはいけないもの | 必須 | 未リリースの機能、非公開の情報。動画は公開後に取り消せないため |
| ユーザーが自分で用意するカット | 任意 | 実機の起動・手元の実写など。台本でその区間を「手持ち素材」と明記する |
| BGM | 任意 | ユーザーが権利を持つ曲を最後に入れるのが基本。音楽生成は頼まれたときだけ |
| 字幕フォント | 任意 | 指定がなければ Noto Sans JP など再配布できるフォント |
| 実測値 | 任意 | 起動時間・処理速度などの数字は、ユーザーの実測に合わせる。推測で書かない |

## 2. 台本と字幕を書く

作業ディレクトリ（例: `video/`）に次のファイルを作る。対象アプリのリポジトリに置く場合は、コミットするかをユーザーに確かめ、しないなら `.git/info/exclude` に入れる提案をする。

- `scripts.md`: 台本。全体のタイムライン、シーンごとの表、VO 原稿の通し、収録の指示、素材の一覧、チェックリスト
- `scripts.vo.srt`: 読み上げ用の原稿。srt-dubbing に渡す。英字・略語・人名・記号を、TTS が正しく読める書き方に開く（例: MySQL → マイエスキューエル、20% → 20パーセント、`SQLite` → `S Q Lite`）
- `scripts.<字幕の言語>.srt`（例: `scripts.ja.srt`）: 視聴者向けの字幕。焼き込みに使う。表記は普通の書き方のまま

音声と字幕が同じ言語でも、読み上げ用と字幕用は別のファイルにする。字幕に「マイエスキューエル」と出すわけにはいかず、TTS に「MySQL」を渡すと読み違えるため。音声と同じ言語の字幕を CC として別に出すなら、読みを開いていない `scripts.<音声の言語>.srt` も作る（音声と字幕が同じ言語なら、字幕用のファイルがそのまま使える）。録音で VO を用意する場合は、読み上げ用の原稿は台本として渡すだけでよい。

### タイムライン

- 尺は提出先の上限より短くてよい。短い方が通しで見てもらえる。数分の動画なら、冒頭のつかみ（10〜15 秒）→ 課題 → タイトル → デモ → 特徴 → 締め、が基本の形。
- シーンごとに「VO / 字幕 / 画（何を映すか、素材の出どころ）」を表にする。画の出どころは、収録（Playwright）、手持ち素材、コードで描く（Remotion）、AI 生成のどれかを明記する。
- 収録区間は、操作の時刻を動画全体の絶対時刻で書く。収録スクリプトはこの時刻をそのまま使う。

### 内容の確認

台本に書いた操作と機能は、書いた時点で実装と照らし合わせる。動画は公開後に直せないので、間違いはここで潰す。

- ショートカットキー・メニュー名・ボタン名・画面の文言は、ソースコード（キーバインドや文言の定義）か実際の画面で確かめる。記憶やドキュメントだけに頼らない。ドキュメントが古く、実装と食い違っていることはよくある。
- 未リリースの機能、GUI から操作できない機能は台本に入れない。画面に映り込むなら、収録時に隠すか、ユーザーに伝える。
- 数字（起動時間、価格、対応 OS）は、実測か公開情報に合わせる。

### 字幕（SRT）

- すべての SRT でキュー番号と時刻を一致させる。訳や読みの対応が崩れないようにするため。
- 1 キューは 1〜2 行、日本語なら 1 行おおむね 16〜20 字。英数字は半角で幅が半分なので、0.5 字として数える（「GitHub Actions の予算枠が」は約 13 字）。読む速さの目安を当てはめるときも同じ数え方をする。読み終わる前に消えない長さにする（日本語で 1 秒 4〜5 字が目安）。
- srt-dubbing は 1 キューの音声をその表示時間に収まるよう速める（最大 2 倍）。読み上げ用の原稿は、キューの長さに対して詰め込みすぎない。英語なら 1 秒 2.5 語程度まで。
- キュー同士を重ねない。書いたら番号の連続、時刻の単調増加、重なりがないことをスクリプトで確かめる（工程 7 でも同じ確認を使うので、`check-srt.mjs` のような小さなスクリプトにしておく）。

### 字幕は後から直せるようにしておく

ユーザーは書き出した動画を見てから、字幕の言い回しや表示時刻を自分で直したくなる。直したら書き出し直すだけで反映されるよう、最初から次のように作る。

- **字幕の正本は SRT にする**。字幕の文言を TSX や `scripts.md` の表から読み込まない。Remotion は書き出しのたびに SRT を読み直す（`references/remotion.md` の prepare.mjs）。`scripts.md` の表は書いた時点の下書きで、SRT と食い違ったら SRT が正しい。
- **シーンの切り替えを字幕に縛りすぎない**。シーンの区間は台本のタイムラインの秒数で決め、キューの時刻から計算しない。キューの時刻を少し動かしても映像が崩れないようにするため。
- **どのファイルを直せばよいかを伝える**。台本と字幕を渡すときに、次の対応を書いて伝える。

| 直したいもの | 編集するファイル | 書き出し直すときに要る作業 |
|:--|:--|:--|
| 焼き込む字幕の文言・改行 | 字幕用の SRT（例: `scripts.ja.srt`） | 書き出し直しだけ |
| 字幕の表示時刻 | すべての SRT（時刻をそろえる） | 書き出し直し。VO を合成している場合は VO も作り直す |
| ナレーションの文言や読み | 読み上げ用の SRT（`scripts.vo.srt`） | 合成なら変わったキューの VO を作り直す。録音なら録り直しをユーザーに頼む |

## 3. 映像素材を作る

- アプリ: `references/source-app.md` に従い、Playwright で台本の時刻どおりに操作して収録する。
- スライド: `references/source-slides.md` に従い、ページごとの画像にして台本の時刻に割り当てる。
- コードで描くシーン（つかみ、図解、締め）は工程 5 で Remotion に描く。
- 手持ち素材はユーザーから受け取り、工程 5 で切り出す。

## 4. VO を用意する

`references/audio.md` に従う。srt-dubbing で読み上げ用の SRT（`scripts.vo.srt`）から合成するか、ユーザーの録音ファイルを受け取る。どちらでも、動画の 0:00 から並んだ 1 本のファイル（`vo.mp3`）にそろえる。

## 5. 編集して書き出す

`references/remotion.md` に従い、Remotion で全シーンを組み、字幕を焼き込み、VO と BGM の音量をそろえて書き出す。字幕あり版と字幕なし版（CC を別に出す用）の両方を書き出せるようにしておく。

## 6. 公開前に確認して報告する

（工程 7 で書き出し直したときも、この確認をもう一度行う）

書き出したら、次を確かめる。

- **尺**: 提出先の上限に収まっているか（ffprobe で測る）。
- **音量**: 全体のラウドネスとピーク（ffmpeg の `ebur128`）。YouTube などに出すなら -14〜-16 LUFS、ピーク -1 dBFS 以下が目安。
- **字幕**: 書き出した動画から字幕のある時刻のフレームを切り出して見る。フォントの代替や文字のはみ出しは、フレームを見ないと分からない。
- **映り込み**: 次のものが映っていないか、手持ち素材も含めて確かめる。見つけたら、勝手に消さずユーザーに判断を仰ぐ。
  - AI 生成サービスの透かし（消してよいかは生成サービスの規約次第）
  - デスクトップのアイコン、ファイル名、通知、ブラウザのタブやブックマーク、メールアドレスなどの個人情報
  - 未リリースの機能のボタンやメニュー
  - 台本と違うデータ（デモ用とは別のアカウント・プロジェクト・ファイルなど）
- **権利**: BGM、フォント（埋め込み・再配布の可否）、AI 生成の映像や音声の利用条件、Edge TTS で合成した音声の利用、提出先の規定。
- **ライセンス**: Remotion は個人と従業員 3 人以下の会社は無料、それ以外は有料のライセンスが要る。会社の成果物として作るなら当てはまるかをユーザーに確かめてもらう。

報告では、出力ファイルのパス、尺、ラウドネス、確かめたことと確かめていないこと（見ていないフレーム、推定で置いた値）、ユーザーの判断を待つ項目を分けて書く。見ていないものを確認済みと書かない。

## 7. 台本・字幕が直されたら書き出し直す

「台本を直したので書き出し直して」と言われたら、何が変わったかを確かめてから、必要な作業だけをやり直す。全部を作り直すと時間がかかり、直していない部分まで変わってしまう。

1. **変わったファイルを特定する**。台本・字幕・素材の更新日時を、前回の書き出し（`out/final.mp4`）と比べる。git 管理していれば `git diff` で中身も見る。「台本を直した」と言われても、実際には SRT だけが変わっていることがある。変わっていないファイルは報告で触れる（例: 「`scripts.md` は変わっていなかったので、表の方も直したつもりなら教えてほしい」）。
2. **SRT を検査する**。番号の連続、時刻の単調増加、重なりがないこと、すべての SRT の番号と時刻が一致していることを確かめる。崩れていたら書き出さず、どのキューかを示してユーザーに直してもらう。ユーザーの直した文言は、こちらで書き換えない。
3. **影響のある工程をやり直す**。
   - 字幕用の SRT だけ → 書き出し直すだけ。字幕の言い回しを変えたら、読み上げ用の原稿も合わせて直すかをユーザーに訊く（同じ言語なら、字幕とナレーションの言い回しがずれるため）。
   - 読み上げ用の SRT の文言や読み → srt-dubbing なら変わったキューの VO を作り直す（`references/audio.md`）。録音なら、どのキューを録り直せばよいかを伝える。
   - キューの時刻 → VO の位置がずれるので、合成なら作り直す。シーンの区間や収録の操作時刻と大きくずれる場合は、映像側を合わせるかをユーザーに訊く。
   - キューの追加・削除（番号が変わる） → すべての SRT の対応を確かめ直し、合成の VO は全体を作り直す。
4. **書き出し直し、工程 6 の確認をする**。字幕が変わった時刻のフレームを切り出し、直した文言が映っていることを見てから報告する。

ユーザーから途中で別の指示（音量の調整など）が一緒に来たら、それも同じ書き出しに含める。
