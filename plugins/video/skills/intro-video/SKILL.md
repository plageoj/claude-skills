# 紹介動画の制作

アプリのデモかスライドを素材に、ナレーション（VO）と字幕の付いた数分の紹介動画を作る。工程は次の 8 つで、どれか一部だけを頼まれたときもその工程の節に従う。工程 2 のあとは、ユーザーが台本を直し終えるまで先に進まない。ユーザーが「確認を挟まず最後まで」と頼んだときだけは止まらずに進め、報告で台本（`scripts.md`）と直し方の表（工程 3）を示す。

1. 入力をそろえる
2. 台本を書く（ユーザーが直して確定させる）
3. 字幕を作り、時刻を決める
4. 映像素材を作る（アプリは収録、スライドは画像化）
5. VO を用意する
6. Remotion で編集して書き出す
7. 公開前に確認して報告する
8. 台本・字幕が直されたら書き出し直す

この skill は手順書で、コードは同梱しない。収録スクリプトや Remotion プロジェクトは、ここに書いた設計に沿ってその場で書く。詳細は工程ごとの参照ファイルにある。

| 参照ファイル | 読むとき |
|:--|:--|
| `references/source-app.md` | アプリのデモを Playwright で収録するとき |
| `references/source-slides.md` | スライドを素材にするとき |
| `references/audio.md` | VO を作る・受け取るとき、音量をそろえるとき |
| `references/remotion.md` | 編集・書き出しをするとき |

## 1. 入力をそろえる

会話やファイルから読み取れないものは、台本を書き始める前に AskUserQuestion でまとめて訊く。言語や尺が後から変わると、台本・字幕・VO・収録のすべてを作り直すことになるため。

| 情報 | 必須 | 用途 |
|:--|:--|:--|
| 動画の目的と提出先 | 必須 | コンテスト応募・LP・SNS など。提出先の規定（尺の上限、形式、AI 生成物の可否）を確かめる。URL があれば読む |
| 素材 | 必須 | アプリ（起動方法と URL）か、スライド（PDF / Marp / pptx / Google Slides） |
| スライドを作り直すか | スライドなら必須 | そのまま使うか、ユーザーのスタイルで作り直してから動画にするか（`references/source-slides.md` の「作り直す」） |
| 音声と字幕の言語 | 必須 | 毎回訊く。例: 英語音声＋日本語字幕（吹き替え映画風）、日本語音声＋英語字幕、字幕なし |
| 視聴者 | 必須 | 前提知識と、字幕を焼き込むか CC で別に出すか |
| VO の作り方 | 必須 | srt-dubbing で合成するか、ユーザーが録音したファイルを渡すか（`references/audio.md`） |
| 触れてはいけないもの | 必須 | 未リリースの機能、非公開の情報。動画は公開後に取り消せないため |
| ユーザーが自分で用意するカット | 任意 | 実機の起動・手元の実写など。台本でその区間を「手持ち素材」と明記する |
| BGM | 任意 | ユーザーが権利を持つ曲を最後に入れるのが基本。音楽生成は頼まれたときだけ |
| 字幕フォント | 任意 | 指定がなければ素材の書体にそろえる（`references/remotion.md`） |
| 実測値 | 任意 | 起動時間・処理速度などの数字は、ユーザーの実測に合わせる。推測で書かない |

## 2. 台本を書く

作業ディレクトリ（例: `video/`）に `scripts.md` を作る。対象アプリのリポジトリに置く場合は、コミットするかをユーザーに確かめ、しないなら `.git/info/exclude` に入れる提案をする。

この工程では `scripts.md` だけを書き、SRT はまだ作らない。書いたらユーザーに渡して、直してもらうのを待つ。台本は直されるのが前提で、とくにスライドを素材にするとき、話し手はスライドにないことをその場で話すことが多い。スライドの文言だけから起こしたナレーションは、骨組みにすぎない。台本が固まる前に SRT や VO を作ると、直すたびに作り直しになり、時刻の組み方も台本の長さに引きずられる。

`scripts.md` に書くもの:

- 全体の尺の見込み、音声と字幕の言語、素材
- シーンごとの表: 時刻の目安 / 内容 / 画（何を映すか、素材の出どころ）
- シーンごとのナレーション原稿。話し言葉の地の文で書く。キューには区切らない
- 間を置きたいところ（「ここで 2 秒置く」）。置かないところには置かない。間は台本で指定された場所にだけ入れる（工程 3 で `⏸` 行に書き換える）
- 収録の指示、素材の一覧、チェックリスト

ナレーションは素材に書かれた内容から起こし、素材にない人物の情報を足さない。名乗り（「〇〇です」）、自己紹介、作者や話し手のクレジット、締めの挨拶での名前は、素材に自己紹介のページや作者の表記が明示されているときだけ入れる。合成音声は本人の声ではなく、素材の作者と動画を出す人が同じとも限らないため。表紙に名前が載っているだけなら画面に映すにとどめ、読み上げるかはユーザーに訊く。締めのカードなど Remotion で描く画面にも、素材にない名前や連絡先を足さない。

### 推敲する

台本を渡す前に、ナレーション原稿を yomiyasu スキル（このプラグインの依存として入ったなら `yomiyasu:yomiyasu`、スキルだけを入れたなら `yomiyasu`）で推敲する。原稿は台詞として読まれるので、種類は script にする。推敲は SRT を作る前に済ませる。SRT と VO を作ったあとで推敲すると、字幕の直しを読み上げに写して合成し直すことになる。

- 推敲するのは、字幕にもなる原稿の文言。読み上げ用の書き方（工程 3）は、推敲したあとの原稿から作る。
- 素材に書かれた事実と数字は、推敲でも変えない（yomiyasu も意味を変えない決まりで直すが、変わっていないかを読み比べる）。
- yomiyasu が入っていなければ推敲を飛ばし、報告でそう書く。

渡すときに、ユーザーに頼むことを添える:

- スライドにない話（実際の発表で話したこと、補足、脱線）を足してほしい。発表者ノートや発表の録音・文字起こしがあれば、それを下敷きに書き直す。
- 解釈して言い換えた箇所（略語の意味、図の読み取り、引用・詩歌・キャッチコピーのような言い換えてはいけない文言）を確かめてほしい。迷ったら言い換えずに原文のまま読む。
- 読み方の分からない語（社名、人名、ID）。ID や URL は画面に出すだけで読まないことも多い。

### タイムライン

- 尺は提出先の上限より短くてよい。短い方が通しで見てもらえる。数分の動画なら、冒頭のつかみ（10〜15 秒）→ 課題 → タイトル → デモ → 特徴 → 締め、が基本の形。
- 画の出どころは、収録（Playwright）、手持ち素材、コードで描く（Remotion）、AI 生成のどれかを明記する。
- この段階の時刻は目安でよい。確定するのは工程 3 で音声の長さが分かってから。

### 内容の確認

台本に書いた操作と機能は、書いた時点で実装と照らし合わせる。動画は公開後に直せないので、間違いはここで潰す。

- ショートカットキー・メニュー名・ボタン名・画面の文言は、ソースコード（キーバインドや文言の定義）か実際の画面で確かめる。記憶やドキュメントだけに頼らない。ドキュメントが古く、実装と食い違っていることはよくある。
- 未リリースの機能、GUI から操作できない機能は台本に入れない。画面に映り込むなら、収録時に隠すか、ユーザーに伝える。
- 数字（起動時間、価格、対応 OS）は、実測か公開情報に合わせる。

## 3. 字幕を作り、時刻を決める

ユーザーが台本を確定させたら（「この台本で字幕にして」など）、`scripts.md` のナレーション原稿から SRT を作る。

- `scripts.vo.srt`: 読み上げ用の原稿。srt-dubbing に渡す。読み方の書き方は下の「読み上げ用の書き方」
- `scripts.<字幕の言語>.srt`（例: `scripts.ja.srt`）: 視聴者向けの字幕。焼き込みに使う。表記は普通の書き方のまま

音声と字幕が同じ言語でも、読み上げ用と字幕用は別のファイルにする。字幕に「マイエスキューエル」と出すわけにはいかず、TTS に「MySQL」を渡すと読み違えるため。音声と同じ言語の字幕を CC として別に出すなら、読みを開いていない `scripts.<音声の言語>.srt` も作る（音声と字幕が同じ言語なら、字幕用のファイルがそのまま使える）。録音で VO を用意する場合は、読み上げ用の原稿は台本として渡すだけでよい。

SRT は台本から機械的に作れるよう、台本の原稿をキューに分けて SRT を書き出す小さなスクリプト（例: `build_srt.py`）にしておく。キューごとに、スライド（シーン）、字幕の文言、読み（字幕と同じなら省略）を持たせる。台本が直されたら、それを再実行すれば作り直せる。

### 読み上げ用の書き方

- 英字・略語・人名・記号は、TTS が正しく読める書き方に開く（例: MySQL → マイエスキューエル、PR → プルリクエスト、`SQLite` → `S Q Lite`）。
- 何度も出る語の読み（日本語の声なら `ChatGPT` → チャットジーピーティー、`AI` → エーアイ）は、置き換えの表にしてスクリプトの頭に置き、読みを書いていないキューに当てる。キューごとに書くと、字幕を直したときに読みの直し忘れが出る。
- 数字＋単位・助数詞（「2023年4月」「4年目」「10月」「0.2%」）は、かなに開かず数字のまま渡す。開くと区切りやアクセントが崩れて、かえって読み違えやすい。開くのは、数字だけで読み方が決まらないもの（バージョンの「2系」を「にけい」と読ませたいときなど）に限る。
- 同じ音で意味の違う語（はし、かみ、きこう）は、かなに開かず、意味の決まる漢字かカタカナで渡す（「橋」「箸」「ハシ」）。かなだけにすると TTS が別の語として読む（「はし」が「わし」と読まれた）。

### キューの分け方

- 1 キューは 1〜2 行、日本語なら 1 行おおむね 16〜20 字。英数字は半角で幅が半分なので、0.5 字として数える（「GitHub Actions の予算枠が」は約 13 字）。
- 文の切れ目で分ける。1 文が長ければ読点で分ける。
- すべての SRT でキュー番号と時刻を一致させる。訳や読みの対応が崩れないようにするため。

### 時刻は音声の長さから決める

キューの時刻を、字幕を読む速さ（1 秒あたりの字数）から決めない。TTS は字幕を読むより速く話すので、読む速さで取ったキューは音声が埋めきれず、無音だらけの間延びしたナレーションになる。

- **srt-dubbing で合成する場合**: 仮の時刻で一度合成して音声の長さを測り、時刻を組み直してから合成し直す（手順は `references/audio.md`）。キューの長さ = 音声の長さ（末尾の無音を除く）＋0.1 秒。キューのあとの間は、どこで切れているかで変える。

  | キューのあと | 空ける秒数 | 耳で聞いた長さ |
  |:--|--:|--:|
  | 文の途中（読点で終わる、または句読点がない） | 0.1 | 約 0.4 秒 |
  | 文の終わり（句点） | 0.3 | 約 0.6 秒 |
  | スライド・シーンの切り替え | 0.9 | 約 1.2 秒 |
  | セクション（章）の切り替え | 1.2 | 約 1.5 秒 |
  | 台本の `⏸` 行 | 上の値＋その秒数 | |

  耳で聞いた長さが空けた秒数より長いのは、音声の頭に約 0.2 秒の無音があるため。文の途中で切れたキューの間を短くするのは、TTS が 1 キューの中の読点で置く間（約 0.4 秒）にそろえるため。どこでも同じ間にすると、キューの切れ目だけ読点の間より長く聞こえ、途切れ途切れの話し方になる。
- **録音の場合**: 録音を先にもらい、発話の区間（`silencedetect`）からキューの時刻を決める。
- 組み直したら、字幕が速すぎないかを確かめる。日本語で 1 秒 10 字を超えるキューは、言い回しを短くするか 2 キューに分けるよう提案する。音声がある動画の字幕は、読み切れなくても音で補えるので、音声のない字幕より速くてよい（最大 1 秒 9.5 字の動画で、見た人は速さを気にしなかった）。
- 尺が見込みと大きく違ったら、TTS の速さ（`references/audio.md`）と台本の量のどちらで合わせるかをユーザーに訊く。スライドを作り直した場合、台本を足すときはノートに移した内容から戻す。
- キュー同士を重ねない。書いたら番号の連続、時刻の単調増加、重なりがないことをスクリプトで確かめる（工程 8 でも同じ確認を使う）。
- 時刻が決まったら、`scripts.md` のシーン表の時刻を実際の値に合わせる。

### 間は台本で調整できるようにする

ユーザーは音声を聞いてから、間を足したり削ったりしたくなる。SRT の時刻やスクリプトの数字を直してもらうのは難しいので、SRT を作ったら `scripts.md` のナレーションを 1 キュー 1 行に書き換え、間をそこに書けるようにする。

```markdown
### 背景（p3〜p6）

**p6**

- `33` 結果がこちらです。
- ⏸ 3 秒
- `34` 処理時間は、半分になりました。
```

- 行頭の番号は SRT のキュー番号。会話で「キュー 34」と言えば通じるようになる。
- 自動で入る間（上の表）は書かない。それより長く置くところにだけ、そのキューの次の行に `- ⏸ 秒数 秒` を書く。ユーザーは数字を変える、行を足す、消すで調整する。
- `###` の見出しをセクションの切れ目として扱い、そこの間をセクションの切り替えにする。
- SRT を書き出すスクリプトは、この `⏸` 行と `###` 見出しを読んで時刻を組む。間の秒数をスクリプトの中に持たない。
- 文言と読みの正本はスクリプト側に置き、`scripts.md` の各行と食い違ったら警告を出す。ユーザーが台本の文言だけを直したときに気づけるようにするため。

### 字幕は後から直せるようにしておく

ユーザーは書き出した動画を見てから、字幕の言い回しや表示時刻を自分で直したくなる。直したら書き出し直すだけで反映されるよう、最初から次のように作る。

- **正本は段階で変わる**。SRT を作るまではナレーションの正本は `scripts.md`。作ったあとは、文言と読みは SRT を書き出すスクリプト、間は `scripts.md` の `⏸` 行、時刻はそこから書き出した SRT。ユーザーが SRT を作ったあとで `scripts.md` の原稿を大きく直した場合は、SRT を作り直すか（時刻も組み直しになる）、直した箇所だけスクリプトに写すかを訊く。字幕の文言を TSX から読み込まない。Remotion は書き出しのたびに SRT を読み直す（`references/remotion.md` の prepare.mjs）。
- **シーンの区間を、何に合わせて動くかで決める**。時刻を組み直したり、間を直したりしても、映像が声とずれないようにするため。
  - スライドや、コードで描くシーン: 区間をキュー番号に結び付ける（例: 「p6 は キュー 33 の開始の 0.5 秒前から」）。音声の長さから時刻を組むと、読みや間を直すたびに後ろのキューが動くので、秒数で書くとすぐずれる。強調などの演出もキュー番号で指定する。
  - 収録したテイク: テイクは台本の秒数どおりに撮ってあるので、区間は台本のタイムラインの秒数で決める。VO の時刻を動かしたら、テイクとずれていないかを確かめる。
- **どのファイルを直せばよいかを伝える**。SRT を渡すときに、次の対応を書いて伝える。

| 直したいもの | 編集するファイル | 書き出し直すときに要る作業 |
|:--|:--|:--|
| 焼き込む字幕の文言・改行 | SRT を書き出すスクリプト（例: `build_srt.py`）。急ぎなら字幕用の SRT を直接直してよいが、スクリプトにも写さないと、次にスクリプトを流したとき消える | スクリプトを流して SRT を書き出し、書き出し直す（SRT を直接直したなら書き出し直しだけ） |
| 字幕の表示時刻 | すべての SRT（時刻をそろえる） | 書き出し直し。VO を合成している場合は VO も作り直す |
| ナレーションの文言や読み | SRT を書き出すスクリプトの読み（書き出すと `scripts.vo.srt` に入る） | 合成なら変わったキューの VO を作り直し、時刻を組み直す。録音なら録り直しをユーザーに頼む |
| 間 | `scripts.md` の `⏸` 行 | 合成なら、時刻を組み直して合成し直す（キャッシュが使われ、並べ直すだけ）。録音なら、録音に無音を挟んでから時刻を取り直す（`references/audio.md`） |
| シーンの画（映すもの、強調、収録の操作） | `scripts.md` のシーン表と「画」の欄 | 該当するシーンのコードか収録を直して書き出し直す。字幕と VO はそのまま |
| 話の中身を大きく変える | `scripts.md` | SRT を作り直す（工程 3 からやり直し） |

## 4. 映像素材を作る

- アプリ: `references/source-app.md` に従い、Playwright で台本の時刻どおりに操作して収録する。
- スライド: `references/source-slides.md` に従い、（作り直すならユーザーのスタイルで作り直してから）ページごとの画像にして台本の時刻に割り当てる。ライブで話し手が担っていたもの（めくるタイミング、指し示し）を動画で受け持ち、どこで何をするかは台本の「画」の欄にキュー番号で書く。
- コードで描くシーン（つかみ、図解、締め）は工程 6 で Remotion に描く。
- 手持ち素材はユーザーから受け取り、工程 6 で切り出す。

## 5. VO を用意する

`references/audio.md` に従う。srt-dubbing なら、工程 3 で時刻を組み直した読み上げ用の SRT（`scripts.vo.srt`）で合成したものが VO になる。録音ならユーザーの録音ファイルを受け取る。どちらでも、動画の 0:00 から並んだ 1 本のファイル（`vo.mp3`）にそろえる。

## 6. 編集して書き出す

`references/remotion.md` に従い、Remotion で全シーンを組み、字幕を焼き込み、VO と BGM の音量をそろえて書き出す。字幕あり版と字幕なし版（CC を別に出す用）の両方を書き出せるようにしておく。字幕なしの動画を頼まれたときも、時刻と画の対応に字幕用の SRT（音声と同じ言語）は作り、字幕なし版だけを書き出す。

## 7. 公開前に確認して報告する

（工程 8 で書き出し直したときも、この確認をもう一度行う）

書き出したら、次を確かめる。

- **尺**: 提出先の上限に収まっているか（ffprobe で測る）。
- **音量**: 全体のラウドネスとピーク（ffmpeg の `ebur128`）。YouTube などに出すなら -14〜-16 LUFS、ピーク -1 dBFS 以下が目安。
- **字幕**: 書き出した動画から字幕のある時刻のフレームを切り出して見る。フォントの代替や文字のはみ出しは、フレームを見ないと分からない。
- **映り込み**: 次のものが映っていないか、手持ち素材も含めて確かめる。見つけたら、勝手に消さずユーザーに判断を仰ぐ。
  - AI 生成サービスの透かし（消してよいかは生成サービスの規約次第）
  - デスクトップのアイコン、ファイル名、通知、ブラウザのタブやブックマーク、メールアドレスなどの個人情報
  - 未リリースの機能のボタンやメニュー
  - 台本と違うデータ（デモ用とは別のアカウント・プロジェクト・ファイルなど）
- **権利**: BGM、フォント（埋め込み・再配布の可否）、AI 生成の映像や音声の利用条件、Edge TTS で合成した音声の利用、提出先の規定。
- **ライセンス**: 会社の成果物として作るなら、Remotion の有料ライセンスが要るか（`references/remotion.md`）をユーザーに確かめてもらう。

報告では、出力ファイルのパス、尺、ラウドネス、確かめたことと確かめていないこと（見ていないフレーム、推定で置いた値）、ユーザーの判断を待つ項目を分けて書く。見ていないものを確認済みと書かない。

## 8. 台本・字幕が直されたら書き出し直す

「台本を直したので書き出し直して」と言われたら、何が変わったかを確かめてから、必要な作業だけをやり直す。全部を作り直すと時間がかかり、直していない部分まで変わってしまう。

1. **変わったファイルを特定する**。台本・字幕・素材を、前回の書き出しで `out/` に控えた SRT や git の履歴と中身で比べる（`git diff`、控えとの `diff`）。更新日時だけで決めない。古い日時のまま差し替えたファイルを見落とすため。「台本を直した」と言われても、実際には SRT だけが変わっていることがある。変わっていないファイルは報告で触れる（例: 「`scripts.md` は変わっていなかったので、表の方も直したつもりなら教えてほしい」）。
2. **SRT を検査する**。工程 3 の確認（番号の連続、時刻の単調増加、重なり、SRT 同士の番号と時刻の一致）を流す。崩れていたら書き出さず、どのキューかを示してユーザーに直してもらう。ユーザーの直した文言は、こちらで書き換えない。
3. **影響のある工程をやり直す**。
   - 字幕用の SRT だけ → 書き出し直すだけ。ただし音声と字幕が同じ言語なら、字幕の言い回しを変えたキューは読み上げ用の原稿も合わせて直し、VO を作り直す。字幕と声の言い回しがずれると、見る人は読みながら聞いて引っかかる。字幕を yomiyasu などでまとめて直したときも同じで、読点を削っただけのキューも読みに写す（間の置き方が変わる）。ユーザーが字幕だけ直したいと言ったときは写さない。
   - `scripts.md` のシーン表や「画」の欄だけ → 該当するシーンのコードか収録を直す。SRT と VO は作り直さない。
   - `scripts.md` のナレーション原稿 → SRT を作り直し、工程 3 の手順で時刻も組み直す。台本の直しが一部だけなら、直したキューだけを SRT に写してもよいかを訊く。
   - 読み上げ用の SRT の文言や読み → srt-dubbing なら変わったキューの VO を作り直し、音声の長さが変わったぶん後ろの時刻を組み直す（`references/audio.md`）。録音なら、どのキューを録り直せばよいかを伝える。
   - キューの時刻 → VO の位置がずれるので、合成なら作り直す。シーンの区間や収録の操作時刻と大きくずれる場合は、映像側を合わせるかをユーザーに訊く。
   - キューの追加・削除（番号が変わる） → すべての SRT の対応を確かめ直し、合成の VO は全体を作り直す。
4. **書き出し直し、工程 7 の確認をする**。字幕が変わった時刻のフレームを切り出し、直した文言が映っていることを見てから報告する。

ユーザーから途中で別の指示（音量の調整など）が一緒に来たら、それも同じ書き出しに含める。
