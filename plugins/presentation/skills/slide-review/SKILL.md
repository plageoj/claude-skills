# スライド評価

完成したスライドを、内容のレビューと、ぺんたのスタイル定義（`references/principal.md`）に照らした評価の二つの面から見て、修正提案を返す。評価の目的は「話しながら見せるスライド」として機能するかを確かめること。資料として単体で読ませるための改善は目的にしない。

最初に `references/principal.md` を読む。判定基準はすべてそこにあり、この SKILL.md は手順だけを定める。

## 1. 入力をそろえる

評価には次の情報が要る。会話やファイルから読み取れないものは、評価を始める前に AskUserQuestion でまとめて訊く。タイマー性（枚数と時間）や聴衆への適合は、これがないと判定できないため。

| 情報 | 必須 | 用途 |
|:--|:--|:--|
| スライド本体 | 必須 | PDF / Marp / Google Slides |
| 発表時間 | 必須 | 秒/枚の判定 |
| イベント名・形式 | 必須 | LT か登壇か、技術系か非技術系か |
| 聴衆 | 必須 | 前提知識に合っているか |
| 発表の目的（持ち帰ってほしいこと） | 任意 | 分からなければスライドから読み取り、講評で「こう読めた」と示す |
| 発表者ノート・台本 | 任意 | あれば話の流れの判定に使う |
| 発表環境（会場 PC・自分の PC など） | 任意 | フォントの環境依存ルールを適用するか決める |

シリーズものの LT でも、前回のスライドは求めない。初見の聴衆として評価する。

## 2. PDF を用意する

計測スクリプトは PDF と Marp を受け付ける。

- **PDF**: そのまま使う。
- **Marp（`.md`）**: スクリプトが marp-cli で PDF に変換する。npx と Chrome が要る。
  - 日本語フォントが見つからないとスクリプトは止まる。ユーザーに日本語フォントを入れてもらうか、Marp で書き出した PDF をもらう。
  - Marp で指定されたフォントがこの環境にないときは、代替フォントで描画したことが summary.md に出る。その場合、折り返しや見た目は実際の発表とずれうるので、講評でそう断る。
- **Google Slides**: 次の順に試す。
  1. 共有リンクが公開なら `curl -L -o slides.pdf "https://docs.google.com/presentation/d/<ID>/export/pdf"`。`file slides.pdf` で PDF か確かめる（HTML ならログインが要る）。
  2. Google Drive コネクタがあれば `download_file_content`（`exportMimeType: application/pdf`）で取得し、base64 をデコードして保存する。発表者ノートは `read_file_content` で読める。
  3. どちらもできなければ、ユーザーに「ファイル > ダウンロード > PDF」で書き出してもらう。
- **pptx**: スクリプトが LibreOffice（`soffice`）で PDF に変換する。python-pptx があれば発表者ノートと指定フォントも読む。LibreOffice の描画は PowerPoint と完全には一致しない（フォントの置き換えで折り返しが変わる）ので、講評でそう断る。LibreOffice がなければ PDF に書き出してもらう。

作業ファイルは評価対象のリポジトリに置かず、一時ディレクトリ（スクラッチパッドがあればそこ）に置く。

## 3. 計測する

```bash
python scripts/analyze.py <slides.pdf|slides.md|slides.pptx> <作業ディレクトリ> --minutes <発表時間（分）> [--pages 1-60]
```

一部のスライドだけを評価するときは `--pages` で範囲を指定する。スライド番号は元の番号のまま報告される。

pymupdf が要る（pptx の発表者ノートを読むには python-pptx も）。入っていなければ、一時ディレクトリに venv を作って `pip install pymupdf` する。

出力:

- `summary.md`: まずこれを読む。見出しの流れ、秒/枚、フォント、文字色、ページごとの機械検出
- `sheets/sheetN.png`: 幅 320px のサムネイルを 4×3 に並べた一覧。**サムネイル判定はこれで行う**
- `full/pNN.png`: 幅 1280px の画像。細部の確認に使う
- `analysis.json`: ページごとの全文、文字サイズ（PowerPoint 換算）、コントラスト比、配色など。Marp では発表者ノート（`notes`）も入る

機械検出はあくまで候補。最終判断は次の点に注意して自分で行う。

- **24pt / 18pt 未満**: 出典・注釈・ネガティブな内容など「読ませない文字」は 18pt まで許される。ヘッダー・フッターは共通要素としてまとめて報告されるので、一度だけ判断すればよい。
- **半角スペース候補**: 日本語として定着した語（IT など）はスペースなしでよい。数字と、数を表す変数（「n秒」の n など）は対象外。社名などの固有表記も考慮する。
- **低コントラスト**: 背景色は行の周囲から推定しているので、グラデーションや写真の上では誤検出がある。画像で確かめる。
- **数字だけのスライド**: 「3ヶ月後」のような演出や図中の数字は対象外。

## 4. 内容をレビューする

スタイルの評価とは別に、発表の中身を見る。スタイル定義を読んだ目で見ると、文字サイズや枚数に注意が寄り、本番で事故になる内容の問題を見落としやすいため、別の工程として行う。

Agent ツールが使えるなら、このレビューはサブエージェントに任せる。渡すのはスライドの PDF（またはページ画像）、全文と発表者ノート（`analysis.json`）、イベント名・発表時間・聴衆だけにし、`principal.md` は渡さない。スタイルに引きずられない読み方をしてもらうため。使えなければ、スタイルの評価に入る前に自分で行う。

見ること:

- **未完成の痕跡**: 「【要確認】」「○○」「TODO」、プレースホルダの残り
- **誤字脱字・表記揺れ**: 同じものを別の言葉で呼んでいないか（例: 規則／規約）
- **話の整合**: タイトルや冒頭の問いが回収されているか。まとめが本文と対応しているか。本文に出てこない言葉がまとめに出ていないか
- **主張と根拠**: 主張に具体例・結果・数字が伴っているか
- **スライドとノートのずれ**: ノートが別のスライドの内容になっていないか、重複・欠落がないか、問題スライドのノートに答えが入っていないか
- **事実と数値**: スライド間・スライドとノートの間で数字や時間が食い違っていないか
- **権利とリスク**: 画像の透かしやライセンス、実名・個人情報、第三者への批判と受け取られる表現

本番で事故になるもの（未完成の痕跡、事実の誤り、権利・個人情報のリスク）は NG、それ以外は要改善か提案として、スタイルの指摘と同じ重要度で扱う。

## 5. スタイルを評価する

サムネイル一覧をすべて見てから、`references/principal.md` の三原則に沿って評価する。観点ごとの見方は次のとおり。

話し手が意図して選んだ表現（「n 秒」のような一般化、演出としての言い回し）は、三原則を損なっていない限り直させない。直す理由を三原則のどれかで説明できない指摘は出さない。

### 5.1 メッセージが伝わるか

- 聴衆が持ち帰るもの・してほしいアクションを一文で言えるか。言えなければ NG。
- 最初のスライド（準備中にずっと映る）で興味を引けるか。タイトルと SNS アカウントがあるか。
- 最後のスライドにメッセージがあるか。「ありがとうございました」だけで終わっていないか。

### 5.2 スライドを見れば話をたどれるか

- summary.md の「見出しの流れ」を読み、それだけで話の筋が追えるか。ラベル型の見出し（「プロダクトについて」）は、アジェンダや中扉で位置づけが示されていれば問題ない。
- 前の章に戻らないと理解できない箇所を数える。4 つ以上なら NG。箇条書きの項目数や、順に進む章立ての数は数えない。
- 1 スライド 1 メッセージになっているか。
- 画像が表示されなくても話が成立するか。
- 発表者ノートがあれば、ノートとスライドがずれていないかも見る。

### 5.3 スライド自体がタイマーになるか

- 秒/枚が 20〜30 秒に収まるか。外れていれば、発表時間 ÷ 20〜30 秒 から目標枚数を逆算し、その枚数に合わせる案を示す。多すぎる情報を抱えたスライドは分割し、少なすぎる情報のスライドは統合する。枚数がそのまま時間になることが、スライドをタイマーとして使う前提だから。
- 時間が押したときに飛ばせる部分が、ぱっと見で見分けられるか（「おまけ:」、文字の多い説明的スライド、スライド内の一部のセクション、後で共有する前提の図表など）。
- 飛ばせる部分を除いても話が成立するか。

### 5.4 読ませていないか

- サムネイル一覧で、見出しとメッセージが読み取れるか。読めないスライドは、聴衆がスライドを「読む」ことになる。
- 文字の多いスライド、単純な箇条書きのスライド。順序が重要でなければ、イラストを横に並べてキャプションを付ける形を提案する。
- コードは、読めなくても意味が通じるようキャプションで補われているか。

### 5.5 見た目

- 配色が background / primary / secondary（+ accent）に収まっているか。それ以外の色は明度違いか。
- フォントが 3 種類以内か。環境依存のフォントがないか（発表環境が分かっていれば対象外）。
- コントラストが足りているか。

### 5.6 プラス評価

聴衆参加の仕掛け（挙手、アンケート、問いかけ）、シリーズの連続性（あらすじ・次回予告）、中扉、段階表示、一言スライドなど、`principal.md` の「よく使うパターン」が効果的に使われていれば講評で挙げる。なくても減点しない。

## 6. 報告する

重要度は 3 段階。

- **NG**: `principal.md` の「3. NG」に当たるもの、本番で事故になる内容の問題
- **要改善**: 「4. ルール」に反するもの、内容の弱さ
- **提案**: ルール違反ではないが、良くなる改善

指摘はスライド番号の順に並べ、各指摘に重要度のタグを付ける。発表者は修正するときスライドを頭から順に開くので、ページ順の方が作業しやすい。優先順位は全体講評の「最優先で直すこと」で示す。枚数が多い（おおむね 20 枚超）場合は、全体講評に重要度ごとの件数と NG の一覧も載せる。

```markdown
# スライド評価: <タイトル>

<イベント名> / <発表時間> 分 / <枚数> 枚（<秒/枚> 秒/枚）/ 聴衆: <聴衆>

## 前提

- <ユーザーに確認できなかったことと、置いた仮定。描画環境の違いなど評価の限界>

## 全体講評

- メッセージ: <持ち帰るものを一文で。読み取れなければそう書く>
- 話の流れ: <見出しだけで追えるか>
- 内容: <内容レビューの要点>
- タイマー: <秒/枚、飛ばせる部分>
- 良いところ: <プラス評価>
- 最優先で直すこと: <1〜3 個>
- （枚数が多い場合）指摘の件数: NG n 件 / 要改善 n 件 / 提案 n 件。NG: p19, p52, ...

## スライドごとの指摘

### p3 「<見出し>」
- **要改善** 本文 21pt（PowerPoint 換算）で 24pt 未満。→ <具体的な直し方>
- **NG** 「【要確認】」がそのまま映る。→ <確定した文言に置き換える>

### 全体にかかわる指摘
- <特定のスライドに属さないもの（表記揺れ、ノートのずれのパターンなど）>

## 自動修正の提案
<下記の条件で自動修正できるものを列挙。できない形式ならその旨>
```

指摘には必ず具体的な直し方を書く。「文字を減らす」ではなく、どの文をどう短くするか、どう分割するかまで示す。指摘のないスライドは書かなくてよい。

報告は作業ディレクトリに `review.md` として保存し、内容を会話でも示す。

## 7. 自動修正

修正提案のうち機械的に直せるもの（文字サイズ、半角スペース、表現の言い換え、スライドの分割、最後のスライドの差し替えなど）は、自動修正を提案する。ユーザーが承諾したら実行する。

| 形式 | 修正方法 |
|:--|:--|
| Marp で git 管理されている | 元のファイルを直接書き換える（`git ls-files --error-unmatch <file>` で確認）。差分は git で戻せる |
| Marp で git 管理されていない | `<元の名前>.revised.md` として別ファイルに出力する |
| Google Slides | 編集できるコネクタがあり、ユーザーが許可した場合のみ編集する。Google のファイルを編集する skill があればそれに従う。なければ修正提案のみ |
| PDF / pptx | 編集しない。修正提案のみ |

修正したら `analyze.py` をもう一度実行し、指摘が解消したか、新しい問題（はみ出し、枚数の変化）が出ていないかを確かめて報告する。
