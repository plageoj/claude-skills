# スライド評価

完成したスライドを、内容のレビューとスタイルの評価の二つの面から見て、修正提案を返す。目的は「話しながら見せるスライド」として機能するかを確かめることで、資料として単体で読ませるための改善はしない。最初に `references/principal.md` を読む。判定基準はすべてそこにある。

## 1. 入力

読み取れなければ AskUserQuestion でまとめて訊く: スライド、発表時間、イベント名・形式（LT か登壇か、技術系か）、聴衆。任意で、持ち帰ってほしいこと（なければ読み取って講評で「こう読めた」と示す）、発表者ノート・台本、発表環境（分かればフォントの環境依存ルールを外す）。シリーズものでも前回のスライドは求めず、初見の聴衆として評価する。

## 2. PDF を用意する

計測スクリプトは PDF・Marp・pptx を受け付ける。作業ファイルは評価対象のリポジトリに置かず、一時ディレクトリに置く。

- Marp: スクリプトが marp-cli で PDF にする（npx と Chrome が要る）。日本語フォントがないと止まる。指定フォントがなく代替で描いたら summary.md に出るので、講評で折り返しがずれうると断る。
- pptx: スクリプトが LibreOffice で PDF にし、python-pptx があればノートも読む。描画は PowerPoint と一致しないので講評で断る。
- Google Slides: 公開なら `…/export/pdf` を取得して `file` で PDF か確かめる（HTML ならログインが要る）。Google Drive のコネクタがあれば `download_file_content`（`application/pdf`）、ノートは `read_file_content`。どちらもできなければ PDF に書き出してもらう。

## 3. 計測する

```bash
python scripts/analyze.py <slides.pdf|slides.md|slides.pptx> <作業ディレクトリ> --minutes <発表時間（分）> [--pages 1-60]
```

pymupdf が要る（なければ一時ディレクトリの venv に入れる）。まず `summary.md`（見出しの流れ、秒/枚、フォント、ページごとの機械検出）を読み、サムネイル判定は `sheets/sheetN.png`（320px の一覧）で、細部は `full/pNN.png` で見る。全文・文字サイズ・コントラスト・ノートは `analysis.json`。

機械検出は候補にすぎない。

- 文字サイズ: 出典・注釈・ネガティブな内容は 18pt まで可。ヘッダー・フッターは共通要素として一度だけ判断する。
- 半角スペース: 定着した語（IT）、数字、数を表す変数（「n秒」）、社名などの固有表記は対象外。
- 低コントラスト: 背景色は推定なので、グラデーションや写真の上は画像で確かめる。
- 数字だけのスライド: 「3ヶ月後」のような演出や図中の数字は対象外。

## 4. 内容をレビューする

スタイルの評価とは別の工程にする。スタイルを読んだ目では、文字サイズに注意が寄り、本番で事故になる問題を見落とすため。Agent ツールが使えればサブエージェントに任せ、スライドの PDF、全文とノート、イベント名・時間・聴衆だけを渡す（`principal.md` は渡さない）。

見ること: 消し忘れたプレースホルダ（「【要確認】」「TODO」。例示や問いとして意図して伏せた値は指摘しない）、誤字と表記揺れ、タイトルや冒頭の問いの回収、まとめと本文の対応、主張に根拠があるか、スライドとノートのずれ（別のページの内容、問題のノートに答え）、数字の食い違い、権利と個人情報（透かし、実名、第三者への批判）。本番で事故になるもの（消し忘れたプレースホルダ、事実の誤り、権利・個人情報）は NG にする。

## 5. スタイルを評価する

サムネイル一覧をすべて見てから、`principal.md` の三原則と 3〜4 章に沿って評価する。

- 直す理由を三原則のどれかで説明できない指摘は出さない。話し手が意図した表現（「n 秒」のような一般化、演出の言い回し）は、三原則を損なわない限り直させない。
- 「話が前に戻る」は、前の章に戻らないと理解できない箇所をスライドをまたいで数える。箇条書きの項目数や、順に進む章立ては数えない。
- 秒/枚が外れていたら、時間 ÷ 20〜30 秒から目標枚数を出し、どれを分け、どれをまとめるかまで示す。時間が押したときに飛ばせる部分が見分けられるか、飛ばしても話が成立するかも見る。
- 最後のスライドを直す提案は、メッセージを足すか差し替える形にし、ほかのページの内容を詰め込む形にしない。
- 4.4 のパターンが効いていれば講評で挙げる（なくても減点しない）。

## 6. 報告する

重要度は、NG（principal の 3 章、本番で事故になる内容）、要改善（4 章のルール違反、内容の弱さ）、提案の 3 段階。指摘はスライド番号の順に並べ（直すときに頭から開くため）、優先順位は全体講評で示す。20 枚を超えるなら、重要度ごとの件数と NG の一覧も載せる。

```markdown
# スライド評価: <タイトル>

<イベント名> / <発表時間> 分 / <枚数> 枚（<秒/枚> 秒/枚）/ 聴衆: <聴衆>

## 前提
- <確認できなかったことと置いた仮定、描画環境の違いなど評価の限界>

## 全体講評
- メッセージ / 話の流れ / 内容 / タイマー / 良いところ
- 最優先で直すこと: <1〜3 個>

## スライドごとの指摘

### p3 「<見出し>」
- **要改善** 本文 21pt（PowerPoint 換算）で 24pt 未満。→ <具体的な直し方>

### 全体にかかわる指摘

## 自動修正の提案
```

指摘には、どの文をどう短くするか、どう分けるかまで具体的な直し方を書く。`review.md` として作業ディレクトリに保存し、会話でも示す。

## 7. 自動修正

機械的に直せるもの（文字サイズ、半角スペース、言い換え、分割、最後のスライドの差し替え）は自動修正を提案し、承諾されたら実行する。

- Marp で git 管理下（`git ls-files --error-unmatch`）なら元のファイルを書き換え、そうでなければ `<元の名前>.revised.md` に出す。
- Google Slides は、編集できるコネクタがあり許可を得たときだけ。PDF・pptx は提案のみ。

直したら `analyze.py` をもう一度走らせ、指摘が消えたか、はみ出しや枚数の変化がないかを確かめて報告する。
